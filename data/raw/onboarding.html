Engineering Onboarding

Welcome to the engineering organisation. This page covers what to set up in your first week and who to ask when something is unclear. It is maintained by the developer experience team and updated at the start of every quarter.

Day One: Accounts and Access

Your manager requests your accounts before you start, but several of them need action from you. Check that you can sign in to the identity provider, the source control system, the ticket tracker and the observability platform.

Access to production is not granted on day one and is not granted by default at all. It requires completing the production access training and being added to an on-call rotation. Most engineers do not need production access to do their work, and requesting it reflexively is discouraged.

Development Environment

The supported setup is a container-based development environment. Clone the monorepo, run the bootstrap script, and the script provisions everything else. The first run takes roughly forty minutes because it builds the base images locally.

Native installs are not supported. They work for some people and break for others, and the time the platform team spends debugging bespoke local setups is time not spent on the shared tooling. If the container environment does not work for you, raise it as a bug rather than working around it.

Common bootstrap failures

If the bootstrap script fails with a disk space error, it needs at least sixty gigabytes free. The base images alone are around twenty-five gigabytes and the build cache grows from there.

If it fails during dependency resolution, the usual cause is a stale lockfile from a previous checkout. Delete the cache directory and re-run rather than attempting to repair it by hand.

How We Work

Changes go through pull request review. Every pull request needs one approval from someone who owns the affected area. Ownership is declared in the CODEOWNERS file and the review request is assigned automatically.

Small pull requests are reviewed quickly and large ones are not. A change over roughly four hundred lines will sit for significantly longer, not because reviewers are unwilling but because a large diff cannot be reviewed properly in the gaps between other work. Splitting work into reviewable pieces is a skill worth developing early.

Where to Ask

Ask in the open channel for your area rather than direct-messaging an individual. Direct messages get faster answers for you and no answer for the next person with the same question. Channel questions become searchable history.

There is no expectation that you work things out alone. The rule of thumb is to spend thirty minutes trying, then ask. Spending a day stuck on something a colleague could resolve in two minutes is a worse outcome for everyone than asking early.
